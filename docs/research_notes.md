# Исследование архитектурных основ SeLinOS

## Цель

Создать стартовую x86_64 многосерверную операционную систему поверх seL4 без Linux-ядра. Система должна в будущем предоставлять расширяемый слой совместимости Linux ABI. Каждый сервис и прикладной поток изолирован через собственный TCB, CSpace, VSpace и минимальный набор capabilities. Одно seL4 остаётся единственным привилегированным микроядром.

## Подтверждённые свойства seL4

Официальный учебник seL4 определяет поток как объект **TCB (Thread Control Block)**, представляющий контекст выполнения и управляющий процессорным временем. На один kernel thread создаётся один TCB. Он включает приоритет/MCP, состояние регистров и FPU, capability к CSpace, capability к VSpace, endpoint получения сообщений об ошибках и слот reply capability.

Планировщик seL4 является приоритетным, round-robin для исполнимых потоков равного приоритета. По документации есть и дополнительное разбиение на домены с циклическим статическим расписанием, где кросс-доменные IPC задерживаются до переключения домена. Это полезно для будущего критического сервиса, но **не будет частью первой загружаемой версии**, чтобы не усложнять валидацию.

Официальное руководство по capabilities описывает capability как уникальный неподлежающий подделке токен права доступа к объекту/сущности. CSpace — полный набор capabilities, доступных потоку; CNode — контейнер слотов capabilities. Поэтому изоляция сервисов строится не на соглашении, а на отсутствии у них capabilities друг друга и аппаратных объектов.

> Архитектурное решение: каждый новый пользовательский домен SeLinOS будет включать как минимум отдельные `TCB`, корневой `CNode/CSpace`, корневой объект `VSpace`, IPC-buffer frame и fault endpoint. Общий CSpace или VSpace по умолчанию не допускается.

| Объект seL4 | Назначение в SeLinOS | Кто выдаёт capability |
|---|---|---|
| TCB | Контекст исполнения ровно одного потока | `taskd` через делегированную authority |
| CNode / CSpace | Минимальный список разрешённых объектов | `taskd`; субъект не получает capability на чужой CSpace |
| VSpace | Изолированное виртуальное адресное пространство | `memd`; mappings на основе делегированных frame caps |
| Endpoint | Синхронный IPC к конкретному серверу | `serviced` / владелец протокола |
| Notification | Асинхронные события | Только источнику и адресату события |
| Frame | Данные или IPC-буфер | `memd`; shared frames — лишь по явному договору |
| Untyped memory | Полномочие создать kernel objects | Только доверенному bootstrap/ресурсному менеджеру |
| IRQ control / handler | Устройство и прерывания | Только `deviced`, не прикладным доменам |

## Выводы для Linux ABI

Linux ABI — не один API, а контракт между пользователем и ядром. Необходимо эмулировать в собственных сервисах постепенное подмножество x86_64 syscall ABI. Двоичные программы переходят в ворота `syscall` в user-space ABI; обработчик должен маршрутизировать запрос по IPC к серверу или удовлетворять его локально. Никакой части Linux kernel не запускается или не линкуется в архитектуре.

Первая веха ABI должна быть честно ограничена. Она не обещает работу `apt` или произвольных Debian-пакетов. Базовая начальная группа: `exit`, `write`, `read`, `openat`, `close`, `fstat`, `lseek`, `mmap`, `munmap`, `brk`, `getpid`, `gettid`, `clone` (ограниченный режим потоков), `futex` (локальный), `nanosleep`, `clock_gettime`, `rt_sigaction`, `rt_sigprocmask`, `arch_prctl`, `set_tid_address`, `set_robust_list`. Не все номера или семантика будут объявлены реализованными до появления тестов.

Более поздние обязательные направления: полноценная ELF dynamic loader/runtime, `execve`, `fork`/copy-on-write, pipes, UNIX/TCP sockets, epoll, pty, devfs/procfs, POSIX ACL/UID/GID, TLS entropy, DNS/TLS, файловые форматы пакетов Debian, dpkg, apt, networking и поддержка нужных Linux-program assumptions.

## Изоляция

Сервис не должен получать более широкие полномочия, чем нужны его протоколу.

| Домен | Полномочия в первом дизайне | Не получает по умолчанию |
|---|---|---|
| `initd` | Запуск базовых серверов, контроль здоровья | Frames приложений, IRQ, блочный диск |
| `taskd` | TCB, CNode, запуск/завершение доменов | Прямой доступ к файлам и устройствам |
| `memd` | Делегированная память, VSpace-mapping | Сокеты, диски, IRQ |
| `vfsd` | Именованные файловые объекты, файловый storage capability | Чужие VSpace, TCB приложений |
| `consoled` | Серийный вывод/ввод, endpoint I/O | Управление процессами и памятью |
| `linux-abi` | IPC capabilities к task/mem/vfs/console, ABI-dispatch | IRQControl, direct device memory, root authority |
| Приложение | Свой TCB/VSpace/CSpace, дескрипторы как capabilities | Чужие адресные пространства и серверные control caps |

## Нерешённые технические решения

1. Выбрать микрофреймворк: минимальный custom root task или Microkit, учитывая требование создавать динамические пользовательские домены.
2. Проверить современную доступность/устойчивость x86_64 support и определить закреплённый tag/manifest seL4.
3. Определить стандарт протокола ABI gateway: прямой user `syscall` trap в доверенный диспетчер либо тонкая statically linked libc, выполняющая seL4 IPC. Для бинарной Linux совместимости первое необходимо; на первом этапе это может быть прототип trap/loader.
4. Спроектировать ownership IPC endpoint и отказоустойчивое завершение сервисов.
5. Выбрать развитие файловой системы: initramfs ROMFS на первой вехе, затем user-space VFS с FAT/ext2 или собственный CoW файловый сервис.

## Вне области первого запуска

GPU, графический стек, Wi-Fi, USB hotplug, аудио, SMP performance tuning, SELinux, containers, cgroups, namespaces, POSIX signals full coverage, AF_INET sockets, dynamic linker, `apt`/`dpkg` и произвольные пакеты Debian не входят в первую функциональную веху. Они являются дорожной картой, а не реализованной возможностью.

## Дополнение: шлюз Linux syscall ABI

Справочники Linux man-pages подтверждают, что системный вызов является фундаментальным интерфейсом приложения и Linux kernel, но программы обычно обращаются к нему через обёртки glibc. В типовом случае wrapper переносит аргументы в требуемые регистры, инициирует системный вызов, а затем преобразует отрицательный kernel error code в `errno` и возвращает `-1`. Для отсутствующего вызова стандартная ошибка — `ENOSYS`.

> Проектное следствие: SeLinOS должен сначала обеспечить точную машинную x86_64-конвенцию для входа `syscall` и правила успешного/ошибочного возврата, а затем по одному реализовывать смысл конкретных номеров. Нереализованные номера первоначально возвращают `-ENOSYS`; нельзя подменять их фиктивным успехом.

### Контракт ABI, фиксируемый на первом этапе

| Элемент | Принятое правило SeLinOS ABI v0 | Замечание |
|---|---|---|
| Целевая архитектура | x86_64 / LP64 | Нет поддержки 32-bit x86 ABI в первом релизе |
| Вход | Инструкция `syscall` из приложения | Диспетчер должен сохранять/восстанавливать пользовательский контекст безопасно |
| Номер syscall | `RAX` | Список номеров фиксируется по Linux x86_64 UAPI версии, закреплённой в проекте |
| Аргументы 1–6 | `RDI`, `RSI`, `RDX`, `R10`, `R8`, `R9` | Подлежит проверке по закреплённому UAPI/header test, не должен копироваться из SysV C calling convention |
| Возврат | `RAX`: неотрицательное значение при успехе, `-errno` при ошибке в raw ABI | libc/wrapper ставит `errno` и возвращает `-1`, как ожидают Linux приложения |
| Неизвестный/неподдержанный номер | `-ENOSYS` | Обязательная наблюдаемая совместимость вместо ложного выполнения |
| User pointers | Явная проверка диапазона в адресном пространстве вызывающего домена и безопасное копирование | Сервер не получает прямого неконтролируемого указателя на память клиента |
| FD | Номер в per-process descriptor table, привязанный к capability на объект/endpoint | Linux-подобный API, capability-backed внутренняя реализация |

Номер ABI и регистровая конвенция будут дополнительно подтверждены кодом-тестом на этапе реализации и официальными заголовками выбранного Linux UAPI тега. Пока это проектное требование, а не выданное обещание работающей бинарной совместимости.

### Ошибка исходного предположения, которую надо исключить

C `SysV AMD64 ABI` для обычных функций и Linux `syscall` ABI имеют различную конвенцию четвёртого аргумента. Поэтому переходник нельзя писать как обычный C-call trampoline: он требует короткой ассемблерной точки входа или строго контролируемой последовательности переключения контекста.

[6] **syscalls(2) — Linux manual page.** https://man7.org/linux/man-pages/man2/syscalls.2.html. Системный вызов — фундаментальный интерфейс между application и Linux kernel; описаны взаимодействие с glibc wrapper и объём списка вызовов.

[7] **syscall(2) — Linux manual page.** https://man7.org/linux/man-pages/man2/syscall.2.html. Описывает стандартную библиотечную функцию косвенного вызова syscall, `ENOSYS` для отсутствующего вызова и общие правила возврата/ошибок.

Следующий этап: получить закреплённую x86_64 таблицу UAPI, выбрать минимальную таблицу из первых 25 вызовов и спроектировать пользовательские серверы/IPC протоколы для их семантики.

## Критическое архитектурное решение: где перехватывать Linux `syscall`

Первичный просмотр текущего x86_64 trap-кода seL4 подтверждает, что seL4 владеет переходами `syscall`/`sysenter` между пользовательским и привилегированным режимом. Следовательно, пользовательский сервер не может сам по себе перехватить произвольную инструкцию `syscall` из уже собранного Linux ELF: процессор сначала передаёт выполнение в seL4.

> Поэтому нельзя заявлять, что простой IPC-сервер в userspace обеспечит запуск непересобранных Linux-бинарников. Для такого уровня совместимости нужно либо изменять системный-call dispatch в seL4, либо транслировать/инструментировать исполняемые файлы до запуска. Оба варианта требуют отдельной инженерной и верификационной работы.

| Вариант | Совместимость с непересобранными Linux ELF | Влияние на seL4 / риск | Решение для SeLinOS |
|---|---|---|---|
| Адаптированная libc (`libselinos`) выполняет seL4 IPC | Только приложения, пересобранные для SeLinOS | Ядро не изменяется; хороший старт сервисов | Использовать для загрузочной системы и первых тестов |
| Пользовательская binary instrumentation / транслятор | Возможна для охваченных инструкций, но требует полноценной обработки self-modifying/JIT/динамического линкера | Ядро не меняется, но сложный и неполный путь | Отложить как самостоятельную подсистему `bincompatd` |
| Малое расширение kernel syscall dispatcher: Linux personality | Потенциально лучший путь к raw ABI, если процесс помечен как Linux-personality | Изменяет seL4; все формальные утверждения должны быть заново подтверждены для новой конфигурации | Исследовательская поздняя веха, **не** первый MVP |
| Linux VM / Linux kernel library | Высокая, но использует Linux kernel | Нарушает выбранный пользователем запрет Linux-ядра | Явно запрещено требованиями проекта |

### Принятое решение MVP

Начальный MVP сохраняет исходный seL4 без модификации ядра. Он предоставляет нативную многосерверную POSIX-подсистему и thin `libselinos` для программ, собранных под SeLinOS. Техническая спецификация Linux x86_64 ABI остаётся целью; первая честно реализованная граница — source/API compatibility для ограниченного подмножества, а не неподтверждённая бинарная совместимость каждого существующего ELF.

Позднее проект может добавить отдельный **Linux personality extension**, только если пользователь разрешит форк/изменение seL4 и отдельную верификацию безопасности. Он должен быть отдельным opt-in execution domain, не обязательной частью trusted path базовых сервисов.

[8] **seL4 x86_64 c_traps.c, current source.** https://raw.githubusercontent.com/seL4/seL4/master/src/arch/x86/64/c_traps.c. Использован для первичного подтверждения, что x86_64 userspace return/trap path принадлежит коду seL4; точная точка dispatcher будет проверена локальным закреплённым исходным деревом на этапе сборки.

[9] **seL4 repository tree.** https://github.com/seL4/seL4. Содержит x86_64 `traps.S`, `c_traps.c` и API-код; в проекте будет использован только закреплённый commit/release, не ветка `master`.

### Последствие для обещаний пользователю

Даже после порта `apt` «все Linux пакеты» нельзя считать достижимой характеристикой, пока не реализованы dynamic linking, fork/exec, procfs, sockets, пакетные хуки, устройство и весь необходимый набор ABI. Дорожная карта должна измерять совместимость тестовыми наборами, а не лозунгом.

## Дополнение: официальный CMake-каркас seL4

Официальная документация seL4 описывает сборку проекта через CMake и Ninja в отдельной build-директории; итоговые образы помещаются в `images/`. Для собственного проекта базовая часть build system находится в kernel repository, а сборочные helpers для объединения libraries/binaries/image — в `seL4_tools/cmake-tool`. Официальная структура допускает отдельные каталоги `kernel/`, `projects/` и `tools/cmake-tool/`; `base.cmake` строит kernel/libsel4/elfloader targets, затем проект добавляет user-space libs и targets и завершает configuration target.

> Проектное решение: SeLinOS использует выделенное source tree `/home/ubuntu/selinos/src`, отдельную `/home/ubuntu/selinos/build`, CMake + Ninja, официальный `seL4_tools/cmake-tool` и закреплённый tag seL4 `16.0.0` (`6e7c3b733d296cfd88d5fbf635c96e447a882374`), обнаруженный в официальном Git ref list. Сам tag kernel недостаточен: revisions `cmake-tool`, `elfloader`, `sel4runtime`, `util_libs` и user libraries должны быть явно закреплены в lockfile после проверки взаимной совместимости.

Локальная среда на Ubuntu 24.04 подготовлена и проверена: CMake 3.28.3, Ninja 1.11.1, Clang 18.1.3, QEMU 8.2.2, GCC 13.3 доступны. QEMU будет использоваться только после успешного построения образа.
