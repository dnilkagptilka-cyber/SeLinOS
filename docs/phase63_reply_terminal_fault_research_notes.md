# Phase 63: reply-mediated terminal-fault transition M0 — research notes

## Contract under study

The Phase 62 target is blocked on an x86 user-exception fault generated by `ud2` at `0x60000001`. The Phase 63 experiment may exercise precisely one zero-label `seL4_Reply` to this fault IPC. Official seL4 fault-handling guidance states that a zero-label reply resumes a faulting thread; the kernel may interpret reply message registers according to the fault-specific format. Therefore the follow-up state must be deterministic, bounded, and independently observed.

The candidate terminal transition will use the fault reply only to update the saved instruction pointer to a **deliberately unmapped canonical sentinel address**. The resumed target should immediately generate one badged instruction-fetch VM fault at that sentinel. Root will receive and validate the second fault, deliberately withhold reply, and never issue a second explicit TCB resume.

> This gate would prove one narrowly selected reply-mediated target transition from a user exception to a terminal VM fault. It would not prove a generic exception handler, arbitrary register repair, an exit protocol, cleanup/reuse, ELF execution, process lifecycle, or Linux ABI.

## Safety requirements

The fixed executable `nop; ud2` page and NX stack frame remain Phase 62 inputs. Root must not install any return address, write a stack image, load an ELF, reply a second time, or grant target authority over the fault endpoint. The first fault must be the Phase 62 user exception at `0x60000001`; the second must be an instruction-fetch VM fault at a constant unmapped canonical sentinel.

## Pinned x86 correction

The pinned source `src/kernel/src/arch/x86/api/faults.c` establishes that `Arch_handleFaultReply()` accepts only `seL4_Fault_VMFault` and returns `true` for that type; other types reach `fail("Invalid fault")`. Consequently, an x86 `seL4_Fault_UserException` reply cannot be used to mutate `rip`. The original reply-mutation hypothesis is rejected, not silently weakened.

The supported Phase 63 shape is therefore: first, start with the entry page intentionally unmapped and receive one instruction-fetch VM fault at `0x60000000`; root maps the already initialized `nop; ud2` entry frame into the target VSpace and sends exactly one zero-label reply. The restarted target fetches and completes the `nop`, then fault-delivers the terminal `ud2` UserException at `0x60000001`. Root withholds reply to that terminal UserException. No reply message registers are supplied and no register mutation is claimed.
